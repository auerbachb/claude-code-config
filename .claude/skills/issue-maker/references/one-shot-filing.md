# One-shot filing — file one idea without entering capture mode

The per-issue create flow of `/issue-maker` (its Step 3, sub-steps 1–7), for a caller that files **one** idea and then goes back to what it was doing. Its first caller is the desk's `idea:` / `file:` intent (`desk/skill/ideas.md`, issue #1766). `/issue-maker` runs the same steps inside its capture session, and both create through the same script, `issue-file.sh`, so a filing from either place has the same reflection, duplicate search, labels, seven-section body, and footer.

`/issue-maker`'s `SKILL.md` stays the canonical statement of every rule below; this file is its summary for the one-shot path. A change to Steps 3–8 there updates this file in the same edit.

## The contract

| | |
|---|---|
| **The caller supplies** | the idea text, the target repo (`owner/name`, already verified), and the mode: `default`, or `rapid-fire` when the operator said "just file it" |
| **The caller gets back** | for each issue filed: its URL, number, title, and applied labels (`issue-file.sh --json`), plus the decision points to report |
| **Not part of it** | the capture session log and its banner, `/issue-maker` Step 2's refusal rule, Step 9's log row, and Step 9c's inline-run offer. A one-shot filing never switches the caller's thread into capture mode |

## The steps

Every `gh` call passes `--repo <the target repo>`. Questions go through the caller's own channel: the desk asks in plain text, never through the menu tool (`desk/skill/ideas.md`). `tier-inference.md` sits beside this file; `autofile-dedup.md` and `time-estimates.md` are read through the standard candidate order — `$HOME/.claude/skills-worktree/.claude/reference/`, then `$HOME/.claude/reference/`, then `.claude/reference/` — and a doc that does not resolve is one `DEGRADED:` line, never a skipped step. Without `time-estimates.md`, use `/issue-maker` Step 5's fallback rows: Light `Est: 60–90 min · plan on 90`, Standard `Est: 120–180 min · plan on 180`, Heavy `Est: 210–300 min · plan on 300`, XL `Est: 180–360 min · plan on 360`. XL is only for a deliberate move past Heavy (an `XL` tier or size label, or a recalibrated actual), never inferred from the idea's wording.

1. **Reflect** — `/issue-maker`'s top-level rule, every time, before and after drafting: narrow (is the real ask smaller?), expand (should an adjacent concern ride along?), split (is it two issues?), size (can one Phase A/B/C pipeline land it as one reviewable PR — `/subagent` Step 4 criterion 3, and a planning bound above the split threshold, 180 minutes by default, is a split trigger too), ambiguity (a word that changes the issue), and the assumptions you encoded. You make these calls and report them afterwards as decision points. Ask first only when a call is blocking: the ask is clearly two separate issues and one combined issue would be wrong, a word is so ambiguous the body cannot be written, or the split would need **more than 5 increments**. An ask that fails the sizing check becomes an ordered increment chain, each increment's own bound at or under `INCREMENT_BOUND_MIN` (120 minutes by default): follow `/issue-maker`'s "Increment issues" (Step 5) and "Linking an increment chain" (Step 8) for each member, head first. The one exception is the time trigger with **no natural seam**: do not force one. File the single issue with its long estimate, and report that estimate as a decision point naming the bound and that no clean seam was found.
2. **Search for duplicates** with `issue-dedup.sh`, resolved through the standard candidate order (`$HOME/.claude/skills-worktree/.claude/scripts/`, then `$HOME/.claude/scripts/`, then `.claude/scripts/`), with 2 to 6 significant words from the title **and** the problem statement and `--repo <the target repo>`. Exit 1 is a clean "nothing found"; exit 2 or 4 means the search did not run — fall back to `gh issue list --repo <repo> --search "<words> in:title" --state all` and say `DEGRADED:` in one line. Classify the top candidate with `autofile-dedup.md` (strong / weak / none). **Default mode pauses on a strong or exact-title match**; a weak match files and becomes a decision point ("possibly overlaps #N"). Rapid-fire pauses only on an exact title match.
3. **Draft the body** from `issue-file.sh --template`: the seven sections in order — Background, Problem, Proposed solution, Acceptance Criteria, Test Plan, Notes / Open questions, Estimate — and the footer `_Captured via /issue-maker._` as the last line. The first three are functional and conversational (what the operator experiences and what changes, no file paths unless the file is the point); implementer detail goes in Acceptance Criteria, Test Plan, and Notes. The Estimate is one line from `time-estimates.md` for the inferred tier (`tier-inference.md`: Heavy, Standard, or Light), `Est: {lo}–{hi} min · plan on {bound}`. Optional `## Related Issues` (step 6) sits after Estimate, before the footer.
4. **Title** — at most 70 characters; trim it yourself and report the trim.
5. **Labels** — from the content, only labels the repo has: `bug`/`fix`/`broken` → `bug`; `feature`/`add`/`new` → `feature`; `refactor`/`clean` → `refactor`; `docs`/`documentation` → `docs`; `skill` → `skill`; `rule` → `rule`; a stated tier → `complexity:quick|light|medium|heavy`. `issue-file.sh` drops any the repo lacks and the four that would hide the issue from `/pm` (`blocked`, `on-hold`, `wontfix`, `duplicate`); report what it dropped.
6. **Cross-references** — each `#N` the idea names, verified with `gh issue view N --repo <repo> --json number`, becomes a `## Related Issues` line: `- Related to #N`, `- Depends on #N` (for "depends on" or "blocked by"), or `- Blocks #N`.
7. **Create** with `issue-file.sh --repo <repo> --title <title> --body-file <file> [--label <name>]... --json`. Exit 0 → `{"repo", "number", "url", "title", "labels", "dropped_labels"}`. Exit 3 → a check failed and nothing was sent: fix what it names and run it again. Exit 4 → `gh` failed, and the issue may have landed anyway (a lost response after the write): check the repo's newest issues before filing again. Exit 2 → the call itself was malformed. On any non-zero exit there is no URL to print.
8. **Report** — one to three sentences on what was filed, in plain functional terms; then, in default mode, the decision points (scope calls, split or chain, the trimmed title, labels applied and dropped, a near-duplicate, assumptions); then the issue URL as the **closing line**. Rapid-fire skips the decision points. A chain or a split reports each member's URL as it is filed and closes on the last one.

## Why the shared script

The mechanical checks — sections, footer, title length, labels, no assignee, a URL that names the right repo — are the part that must never differ between the two callers, so they live in `issue-file.sh` rather than in either skill's prose. The footer is what the desk's Reviews sync uses to bring a filed issue back as a Review; an unassigned issue without an excluded label is what `/pm` ranks.
