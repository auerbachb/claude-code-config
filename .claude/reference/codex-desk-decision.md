## Control and answer delivery

The store has one `control_session` per schema. An operator choosing Codex would explicitly hand off control to its exact chat ID with `register-control SESSION` and immediately run `tick --session SESSION`. The latest registration wins and clears `tick_at` on a change. The old Claude loop detects replacement and exits. Its scoped tick also refuses under the registration lock, protecting the feed cursor even if a handoff lands between the loop's status read and tick. A replacement heartbeat stops when its ID is refused. The operator can hand control back by starting `/desk` in Claude. Read-only views can use the store while either app owns control. Existing `answer` and `set-resolve` writes do not fence the controller, so a future client should recheck ownership before submitting and verify concurrent answer behavior in its build tests. A second controller must never tick under the first controller's ID.

Store the answer first. For a same-machine Codex worker, reuse the existing profile-bound adapter where verified and authorized. The installed Codex CLI (0.166.0) describes `queue --thread ... --message ...` as queueing a message and documents `--resume` separately. The adapter queues `human-queue: D-<n> answered` without `--resume`. A successful enqueue confirms the pointer was accepted. An idle thread may still need the operator to resume it. Workers read the answer from the store and acknowledge it after applying it.

With a Claude controller, existing Claude wake-up looks up a running session in that controller's profile and sends a pointer if it has an address. A Codex controller has no verified Claude address bridge, including across accounts. Record store-only delivery and let the worker check `pending-for SESSION` or the next worker on the issue read the parked answer with `pending-for --repo OWNER/NAME --key KEY`. Use the same store-only path for Cursor, imports, and Codex routes on another machine or an unmatched profile. Capture reverts to each worker’s own interface once the desk’s tick is stale. Keep message payloads to Decision pointers and record the delivery result the transport actually returned.

## Verification and next decision

The repository’s `desk.test.sh`, `capture.test.sh`, and `external-decision-sources.test.sh` ran against PostgreSQL 17 in a throwaway cluster on a private Unix socket. All 151 assertions passed (52, 71, and 28 respectively). The scratch-schema fixtures cover controller replacement, loss of freshness, unchanged feed cursor on stale-controller refusal, durable worker-specific answers, and the exact queued Codex pointer with a fake launcher. No live queue or chat was used for these tests.

Reconsider after a five-minute same-chat heartbeat in an isolated desk profile records successful scoped ticks through an idle interval, an active turn or question, and a restart. Verify the maximum age against `live_desk_max_tick_age_min` and check that replacement leaves the old controller unable to consume the feed. The November investigation verified the store contract and the documented scheduling interface. It did not measure local heartbeat delivery against the store.

The smallest useful first version would show Decisions and one-line Reviews, accept the existing typed replies or a native menu where available, and support explicit controller handoff. Keep day planning, to-dos, Reviews drill-down and a cross-provider wake transport out of that first version. The phone inbox covers Decisions and one-line Reviews from GitHub Mobile. A Codex controller would let the operator handle the same work from their desktop chat. Reuse the desk account binding before enabling live control. Implementation follow-ups are deferred until the heartbeat has been verified.
