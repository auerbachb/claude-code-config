# CodeRabbit Rate Limits & Behavior (Pro Tier)

Full detail extracted from `.claude/rules/cr-github-review.md` (the rule file keeps a summary + pointer to here). Loaded on demand, not every turn.

**Real cap (dashboard-confirmed, issue #1204):** **5 reviews/hour per developer** on Pro (Pro Plus 10, Enterprise 12) — an hourly *burst* limit, not the ~8/hr account-wide this repo modelled. Monthly volume is not the constraint: 290 reviews across two authors sat far below any monthly ceiling while **196 of them (68%) were still blocked**, average wait **87.4h**, and **36% of blocked PRs merged unreviewed**. The banner additionally cites a 7-day attempt history; the two signals do not describe one clean model, and only the hourly number is actionable. When it is reached CodeRabbit posts a `Review limit reached` banner citing its Fair Usage Limits Policy and **names its own retry window** (wording drifts — see the table below). Observed on **223 of 244 PRs** in the 2026-07-22 → 2026-08-21 window; on **183** of those the banner was CodeRabbit's only output, because nothing waited out the stated window. Evidence: `ai-review-tool-audit-2026-08.md`.

**Two signal shapes, only one waitable (observed live on PR #1203).** CodeRabbit reports a limit either as (a) an **issue-comment banner** naming a retry window — the dominant shape, seen on 223 PRs — or (b) a **commit status** `CodeRabbit / success / "Review rate limited"`, which names no window at all. Only (a) can be waited out; (b) has nothing to wait on, so it escalates immediately as before. A PR can show (a) on one SHA and (b) on the next.

**Honour the stated window.** A banner naming a retry window is a bounded, self-healing wait — `escalate-review.sh` keeps emitting `polling_cr` until it elapses instead of escalating past the paid primary. Once elapsed with no review, escalation proceeds unchanged. A banner with no readable window escalates immediately, as before.

**Banner wording drifts — every observed phrasing (keep this list current, issue #1364).** The retry-window sentence has been reworded more than once, and the parser was keyed on the whole sentence, so it silently stopped reading the window and escalated PRs to a *sticky* Greptile assignment mid-allowance:

| Seen | Verbatim retry-window line | Family |
|------|----------------------------|--------|
| 2026-07-16 | `Your next review will be available in 22 minutes.` (future tense: `will be` between `review` and `available`) | adaptive limits |
| through 2026-08 | `**Next review available in:** **12 minutes**` | `Review limit reached` |
| 2026-08-26 → | `**Next included review available in 27 minutes.**` (inserted `included`, colon dropped) | `Review limit reached` |

Parsers must key on the **stable anchors** — `next` … `review available in` … number + unit, case-insensitive, optional colon — never the full sentence. Drift has arrived on **both sides of `review`**, so the allowance is two slots: bounded **0–2 free words before** `review` (an adjective position, where the next insertion is unguessable) and an optional literal **`will be` after** it (a copula with two observed forms). The copula slot stays literal because `lib/pr-state-classify.jq` applies the same pattern with **no author gate**, and `available in <number>` is ordinary prose — a generic bridge there would absorb real findings. CodeRabbit also stamps a **wording-independent marker** on `Review limit reached` comments, which is the durable signal: `<!-- This is an auto-generated comment: rate limited by coderabbit.ai -->`. Both `escalate-review.sh` (retry-window grace) and `lib/pr-state-classify.jq` (rate-limit-notice branch) are keyed this way; **add a row above when a new phrasing appears** rather than patching one parser in isolation — the 2026-07-16 row is what one-sided patching missed, tolerated by the classifier for six weeks while the window parser read zero from it.

**The two families are not interchangeable.** The retry-window *grace* deliberately admits only the `Review limit reached` family (heading prose or marker). The **adaptive-limits** notice is wrapped in a `Full review finished.` auto-reply — it reports a review that already landed and times the *next* one, so there is nothing to wait out on that HEAD and it buys no grace. The classifier tolerates it regardless, because its only question is whether the comment is a finding.

**Local pacing proxy — not CodeRabbit's meter.** `cr_hourly` tracks ~**8** reviews/hour with a rolling 3600s window (`.claude/scripts/cr-review-hourly.sh`: `--check`, `--consume`, `--record-explicit N`; default budget **8**, `CR_HOURLY_BUDGET` = tests only; state in `cr_hourly.events` and `.prs[N].cr_explicit_triggers`). Treat it as **our** self-pacing budget, deliberately kept because an hourly counter cannot model a 7-day allowance and a smaller wrong-shaped number would not predict a lockout either (`ai-review-chain-roles-decision.md` §Explicitly rejected). It never predicts a CodeRabbit lockout — only the banner does. Max **2** explicit `@coderabbitai full review`/PR/hour; surface user at the **2nd** recorded trigger. One commit per fix batch before push. Also ~**50** chats/hour.

**Cooldown / exhausted:** `cr-local-review.md` first; wait out the banner's window, then the escalation gate, which now answers `no_reviewer` instead of a paid hand-off (issue #1897; `review-policy.md` §Paid review authorization). Parallel PRs: stagger (~3–4 CR-triggering pushes/hour).

## Paid on-demand review offers

When the free allowance runs out, CodeRabbit may offer to review now for money instead of waiting — seen live in another thread as an on-demand review "up to $6.75", next to a free one in about 19 minutes. **Always decline** (`safety.md` §Paid AI Reviews; issue #1897): never tick the on-demand checkbox, buy credits, or raise a cap. Continue on the free path — keep polling until `merge-gate.sh` reports met — a free review can satisfy it, or the [no-review override](no-review-override.md) (whose hard stops still apply), even inside the stated retry window (`escalate-review.sh` keeps `polling_cr` while that window is open). After it, follow the escalation gate's `no_reviewer`. Only the owner's explicit approval in chat for that review changes this, recorded as a grant: accept only when `paid-review-grant.sh --offer-check <pr> --vendor coderabbit --offer-price-usd <X> --currency USD` answers `STATUS=consumed` (approved price at or above the offer; `paid-review-approval.md`). Purchases stay with the account owner (`pricing-matrix.md` line 14: "No agent executes a purchase").

**CLI layer is separate.** The CodeRabbit CLI has its own quota — on a public repo, roughly 3 free-OSS reviews before a ~40-minute lockout — independent of the GitHub App's allowance (`feedback_cr_cli_free_oss_tier_cap.md`, `local-review-cli-failure-modes.md`). Neither exhausting the other.

## Does a request made while limited extend the limit? (issue #2256)

**Answer from the public docs** (`docs.coderabbit.ai/management/rate-limits`, read 2026-11-11): a blocked push "does not consume a review or delay when your next review becomes available"; capacity is "limited by earlier reviews in the rolling window, not by the current push", and reviews return "as earlier reviews age out of the window". So a blocked **push** does not extend the window.

**Unknown for an explicit `@coderabbitai review` posted while limited.** The page lists review commands as using one review each, but does not say whether a blocked command is counted, or whether it moves the retry time. Settling it needs one observation: the retry-time banner read before and after a single command posted on a rate-limited PR, against a control PR. No test comment was posted for this issue.

**Consequence for the harness:** the request path posts only `@codeant-ai review`; CodeRabbit is not asked by the harness. The question therefore matters only for a manual `@coderabbitai review`. The availability record (`review-availability.sh`) never posts a request while CodeRabbit is recorded as limited past the request window.

**Parsing:** the retry-window wording is parsed in one place, `.claude/scripts/lib/cr-retry-window.jq`, shared by `escalate-review.sh`, `no-review-override.sh` (availability record) and `review-availability.sh`. Add new wordings to the table above and to that file.
